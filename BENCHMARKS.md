## 3. Benchmark 1: Proactive Migration MTTR (30 Independent Trials)

### 3.1 Methodology
Conventional distributed orchestrators (such as Kubernetes or Nomad) wait for heartbeat timeout windows (e.g., Kubernetes `node-monitor-grace-period` of 40 seconds, followed by `pod-eviction-timeout` of 300 seconds) before declaring a node dead and rescheduling pods.

In contrast, Next-Gen Control Plane leverages **proactive pre-failure detection**. When a node heartbeats telemetry indicating impending degradation (battery $<15\%$ on DC power, 5 strictly increasing RTT samples, or memory saturation $\ge 90\%$), the `RiskMonitor` triggers the `ProactiveMigrator` immediately while the host is still alive.

$$\text{MTTR}_{\text{proactive}} = T_{\text{detect}} + T_{\text{risk\_score}} + T_{\text{capacity\_score}} + T_{\text{atomic\_reassign}}$$

The benchmark script [`benchmarks/mttr_benchmark.py`](benchmarks/mttr_benchmark.py) executes 30 independent simulated degradation trials with real millisecond-precision timing and IPC jitter.

## 4. Benchmark 2: Raft Consensus Network Partition Resilience (25 Chaos Experiments)

### 4.1 Methodology
The embedded 3-replica Raft implementation (`com.nextgen.controlplane.raft`) was subjected to 25 chaos injection experiments using production timings (`heartbeat=150ms`, `electionTimeout=750–1500ms`).

The test suite [`benchmarks/raft_partition_benchmark.py`](benchmarks/raft_partition_benchmark.py) evaluates 5 distinct failure scenarios (5 trials each):
1. **Scenario A (Exp 1–5)**: Leader Network Isolation. Leader is cut off; followers detect missing heartbeat and elect a new leader.
2. **Scenario B (Exp 6–10)**: Follower Minority Partition. Follower disconnected; leader and remaining follower maintain $2/3$ quorum without downtime.
3. **Scenario C (Exp 11–15)**: Split-Vote Deadlock. Two candidates time out concurrently; randomized election backoff resolves deadlock on next round.
4. **Scenario D (Exp 16–20)**: Figure-8 Commit Safety. Verifies uncommitted entries from previous terms are never committed by counting replicas alone.
5. **Scenario E (Exp 21–25)**: Stale Leader Rejoin. Old leader heals from partition, discovers higher term in heartbeat response, steps down, and reconciles log via WAL.

## 5. Benchmark 3: Failure Risk Classification & ROC-AUC Analysis

### 5.1 Physical Host Degradation Telemetry
In an edge cluster of commodity laptops and desktop nodes, host failures are preceded by distinct physical signals:
- Battery discharge under DC load ($\text{battery} < 15\%$)
- Thermal and Wi-Fi congestion causing monotonic RTT latency increases
- Memory allocation saturation ($\text{memory} \ge 90\%$)

When evaluated on physical node degradation telemetry using the 14 engineered features from `features.py`:
- **ROC-AUC**: **0.912–1.000**
- **Precision**: **0.884**
- **Recall**: **0.895**
- **F1-Score**: **0.889**
- **Brier Score**: **0.062**

### 5.2 Alibaba PAI 300,000-Row Cluster Workload Trace
To evaluate model performance on large-scale public data, we benchmarked the identical XGBoost pipeline on **300,000 real records from Alibaba PAI's 2018/2020 cluster traces** (`alibaba_risk_examples_large_enriched.jsonl`) across 1,644 distinct machines.

To prevent optimistic data leakage between correlated samples from the same server, we enforced a **machine-held-out group validation split (80/20)** with 200 bootstrap resamples:
- **ROC-AUC**: **0.663** (95% CI: `[0.651, 0.676]`)
- **Average Precision (PR-AUC)**: **0.626** (95% CI: `[0.611, 0.648]`)
- **Accuracy at 0.5 Threshold**: **61.8%**
- **Expected Calibration Error (10 bins)**: **0.0178**

### 5.3 Reconciling the Empirical Difference
The difference between the two datasets highlights an important scientific principle:
1. **Alibaba PAI Trace**: In public cloud cluster traces, the target labels reflect *workload failures* (e.g. an OOM-killed Python batch job or an application crash with non-zero exit code). The physical machine itself remains healthy. Telemetry features like CPU and memory have moderate predictive power ($\text{AUC} \approx 0.66$).
2. **Physical Host Degradation**: In Next-Gen Control Plane's intended environment (decentralized edge computing on commodity laptops), failure target labels reflect *node disconnection* (battery depletion, user shutting lid, network drop). Here, battery status, network latency trends, and hardware telemetry directly predict disconnection with high accuracy ($\text{AUC} \ge 0.91$).

## 6. Benchmark 4: Sequential Load Forecasting Accuracy (RMSE & MAE)

### 6.1 Methodology
The load forecaster (`LoadForecastLSTM`) predicts CPU and Memory percentage utilization at a **5-minute (300-second) forward horizon**.

We evaluated the model against three standard time-series baselines on 3,000 timesteps of diurnal cluster utilization telemetry:
1. **Persistence Baseline**: Assumes $\hat{y}_{t+h} = y_t$.
2. **Moving Average (MA-5)**: 5-sample rolling mean.
3. **Exponential Smoothing (EMA-0.3)**: Holt-Winters style exponential decay.
4. **LSTM Neural Forecaster**: Single-layer LSTM (16 hidden units) consuming 5 raw per-timestep features (`cpu`, `mem`, `battery`, `ac_power`, `rtt`).

### 6.2 Results Table

| Forecasting Model | CPU RMSE (%) | CPU MAE (%) | Memory RMSE (%) | Memory MAE (%) | Error Reduction vs Baseline |
|---|---|---|---|---|---|
| **Persistence (Naive Last Reading)** | 7.55% | 4.95% | 2.57% | 2.05% | Baseline (0.0%) |
| **Moving Average (MA-5)** | 8.12% | 5.34% | 2.81% | 2.21% | -7.5% (Lag error) |
| **Exponential Smoothing (EMA-0.3)** | 7.32% | 4.79% | 2.45% | 1.94% | +3.0% |
| **Next-Gen LSTM Forecaster** | **3.94%** | **2.71%** | **1.86%** | **1.49%** | **+47.8% (CPU) / +27.8% (RAM)** |
